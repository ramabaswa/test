1. Control architecture

Build one Release Control Service around your existing delivery tools. Agents are bounded workers inside it, not a replacement for CI/CD, change approval or SRE.

Two execution paths: agent tool requests go through the governed agent-tool boundary; trusted workflow activities call narrowly scoped adapters. Both need authorization and audit.

Five responsibilities that must stay separate

PieceDoesNever does
AgentExplains evidence, proposes a next actionApprove, waive, change policy, deploy
WorkflowHolds state, timers, retries, escalationDecide policy
Policy moduleDeterministic allow / deny / hold on trusted factsRely on a model’s opinion
Human authorityAccepts risk for an exact manifest, target, windowGive a generic “yes”
ExecutorRuns the permitted operation with a scoped identityAccept arbitrary digest, target or branch
Ready ≠ approved ≠ deployed ≠ healthy. Evidence must match the exact artifact digest; an approval covers one manifest, so any material change needs a new revision and new approval. This binding is also the strongest control against change drift.

4. Onboarding: three tracks

A. Platform and connectors (once)

  • Confirm real products and boundaries
  • Separate identities: read, nonprod dispatch, prod dispatch, agent tools
  • Typed adapters with retry and dedup
  • Verified event ingress (never trust payload alone)
  • Persistence, outbox, audit, restore test
  • Certify duplicate, timeout-after-success, forbidden target, revoked identity

B. Each service

  • Profile: owners, repos, targets, required controls, approvers, health, recovery, agents, lifecycle
  • Owners approve their own sections; IAM approves target access
  • Shadow run, then one nonprod release plus a failure exercise
  • Production is a separate permission and sign-off

C. Each agent

  • Register purpose, owner, model, prompt version, data class
  • Constrain tools, targets, limits, output schema
  • Evaluate: grounding, injection, forbidden calls, secret leakage
  • Shadow with no write tools, then activate with a review date and kill-switch owner
A service counts as onboarded only when a nonproduction release proves evidence linkage, scope-bound approval, target permissions, observed outcome and safe failure, not when a form is approved.

5. Implementation framework

Contracts before prompts. Build vertically: one service, one target, one complete failure path.

Work packages (order, not a calendar)

WP01 pilot and architecture · WP02 identity and ingress · WP03 profiles and contracts · WP04 read integrations · WP05 workflow foundation · WP06 readiness and dashboard · WP07 read-only agents · WP08 approval bridge · WP09 nonprod executor · WP10 production certification · WP11 optional expansion (PR-fix loop, IaC leases, canary, cost admission, analytics)

First working release does only this

  • One application, one nonproduction target; candidate from an existing successful CI build
  • Collect evidence for that exact candidate; show ready, held or unknown with linked reasons
  • Read-only agents explain blockers and draft notes; approval recorded in the existing authorized workflow
  • Dispatch the existing deployment job via a scoped adapter; observe the result and attach evidence to the change

6. Rules and failure behavior

ConditionRequired behavior
Budget control: limit admitted resource units, SKUs, concurrency and duration with an atomic reservation before provisioning. Budget alerts remain a monitoring input. Per the uploaded playbook’s reading of Microsoft documentation, which I did not verify, Azure budgets do not stop consumption and cost data lags, so this is not a guaranteed invoice cap.

Acceptance tests (specifications, not results)

    Decisions to settle before coding

    • Actual SCM, CI/CD, registry and runtime; reuse one current pipeline
    • Approval stays in the existing ServiceNow process, with explicit manifest-scope linkage
    • Workflow runtime: an existing durable engine if suitable
    • Required controls and freshness per service, owner-approved; no universal risk score
    • Which recovery actions may be autonomous (only preauthorized, tested; never destructive data recovery)
    • Baseline metrics before rollout; no promised ROI

    Four records to implement first

    RecordMinimum fieldsInvariant
    Manifestrelease_id, revision, manifest_digest, service_id, profile_version, commit SHA, build run, artifact digests, config/IaC revisions, target_id, change_id, rollout/recovery refsHash a canonical, versioned material-scope payload; evidence and approval reference that digest

    Authorizationdecision_id, manifest_digest, action, target, window, policy version, approver and role, approved/expires times, revocation referenceRevalidate scope, authority, expiry, revocation and required controls at privileged boundaries

    Event-handling rules

    • Assume at-least-once delivery; deduplicate by source and event ID
    • Commit metadata and an outbox entry in one transaction; publish asynchronously
    • Use version checks to stop conflicting transitions
    • Quarantine malformed or untrusted events; dead-letter persistent failures
    • Re-fetch authoritative state when a late event conflicts
    • An event such as approval.granted is never sufficient authority on its own
